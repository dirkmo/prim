## Python development setup

Python 3.11 or newer is required. Install the local package and activate its
environment from the repository root:

```sh
bash setup.sh
source .venv/bin/activate
prim --help
```

`pyproject.toml` declares the runtime dependency (`tomli-w`) and command-line tools.
`pip install -e .` installs the tools in editable mode. Optional dependencies
are separate: `pip install -e '.[debug]'` adds the terminal debugger;
`pip install -e '.[hdl]'` adds the existing Amaranth tools. Neither is needed
for the TokenForth compiler or Verilog simulations.

The Python implementations live in `src/prim/`:

```text
prim/
    cpu.py             Python CPU and memory interface
    isa.py             Opcode constants, Verilog and TokenForth export
    assembler.py       Assembly and binary disassembly
    tokenizer.py       Scanner and source tokenization
    compiler.py        TokenForth compilation
    artifacts.py       Token/program models, validation and TOML/binary I/O
    tokens.py          Token encoding
    errors.py          Compiler diagnostics
    exporter.py        TOML section -> binary export
    disassembler.py    Annotated program-image disassembly
    debugger.py        Optional terminal debugger
    cli.py             Command-line dispatch
```

Use `prim asm`, `prim tokenize`, `prim compile`, `prim export`, `prim disasm`,
`prim opcodes`, or `prim debug`. Separate `prim-asm`, `prim-tokenize`,
`prim-compile`, `prim-export`, `prim-disasm`, `prim-opcodes`, and `prim-debug`
commands are also available. `python -m prim` exposes the same subcommands.
Each command accepts `--help`.

The old `src/*.py` tool wrappers have been removed. Use, for example,
`python -m prim compile ...` instead of `python src/tokenforth.py ...`.
The Makefile uses the package CLI in the active environment. Library imports
use `prim.cpu`, `prim.tokenizer`, `prim.compiler`, etc. The RTL tests import the installed package without modifying `sys.path`.
See [rtl/README.md](rtl/README.md) for simulation and end-to-end tests.

## Build and debug

From the repository root, with the environment activated:

```sh
make -C src
pip install -e '.[debug]'  # once, for the terminal debugger
prim debug -i build/src/interpreter.tf.toml -u build/src/test.tok
```

The base library is built in three stages: `bootstrap.cf` defines `c,` and
`,`; `prim opcodes --format tokenforth` generates `build/src/opcodes.cf` from
the ISA; `base.cf` adds composite emitters and control words. The generated
words use assembler spellings with a trailing comma: `call,`, `+,`, `>r,`,
`c@,`, `push,`, etc. Each emits only its opcode byte; operands are written
separately with `c,` or `,`. `simend,` emits a simulation marker.

To generate the source separately:

```sh
prim opcodes --format tokenforth build/src/opcodes.cf
```

`prim opcodes` still defaults to Verilog export. Programs importing the base
library can install their reset entry with `[ 'main boot! ]`, which writes
`PUSH16 main; CALL; BREAK` at address zero and preserves the current HERE.

The Makefile writes generated files to `build/src/`. Convenient targets such
as `make -C src base.tf.toml` still work. Override `OUT_DIR` to choose another
output directory, or `PYTHON` to choose the interpreter. Changes to Python tool
modules, `pyproject.toml` or the Makefile trigger a rebuild. `make -C src clean`
removes only the twelve named build outputs; it preserves other files and does
not clean up files generated by older Makefile versions under `src/`.
Run `make -C src` once before using the IDE tokenizer/compiler launch entries
so their output directory exists.

To debug a standalone example:

```sh
prim tokenize -i src/examples/hello.cf -it build/src/base.tf.toml -o build/src/hello.tok.toml
prim compile -i build/src/hello.tok.toml -o build/src/hello.tf.toml
prim debug -i build/src/hello.tf.toml
```

Use Right Arrow for a single instruction, Down Arrow to step over a call,
`run` to continue, `help` for commands and Escape or Ctrl+D to exit.
Memory/code views and the `r` command inspect CPU-visible values without
consuming UART input. `uart <text>` queues UTF-8 bytes, without an implicit
newline. Only CPU reads consume input. `reset` restores CPU and memory,
replays the initial `-u` file bytes and discards later interactive UART input
and temporary step-over breakpoints. User breakpoints remain set.
UART input is optional: without `-u`, the queue starts empty. An explicitly
specified unreadable input file is reported as an error. The debugger models
RX status at `0xfffe` and RX data at `0xffff`; this RX extension is not part
of the current TX-only RTL system.

Python checks (debugger tests require the debug extra):

```sh
python -m unittest discover -s src -p 'test*.py'
```

## The Plan

Implement a primitive stack machine and a ColorForth like language that I call __TokenForth__.

## Stack Machine

The CPU has 8-bit opcodes, a 16-bit ALU, 8-bit and 16-bit memory accesses, 16-bit data and return stacks. It implements the basic Forth instructions.

```asm
NOP
CALL
JP, JPZ
AND, OR, XOR, NOT, SR, SL, SRW, SLW
+, -, CARRY
<, <u
SWAP, OVER, DUP, NIP, ROT, -ROT, DROP, RDROP
>R, R>
@, !, c@, c!
PUSH8, PUSH
```

Only `PUSH` and `PUSH8` have immediate data.

Bit #7 of an opcode represents the return bit.

Other instructions can be added easily, since there are a lot of unused opcodes.

The Python CPU is implemented in `src/prim/cpu.py`; the assembler/disassembler
is implemented in `src/prim/assembler.py`.

## TokenForth

A tokenizer (`src/prim/tokenizer.py`) parses the source code and converts it into a binary representation. This is compiled by `src/prim/compiler.py`. Words in immediate mode are executed during compilation by the CPU.

The TokenForth language recognizes the following token types:

### DEFINITION
Defines a word (word as understood in Forth context). Definitions are prefixed with `:` (colon).

Example:
```
:wordname
```
This is basically like a label in a "normal" assembly language.

### LITERALS
Literals compile raw data and are prefixed with `#`. There are two literal types, one for numbers, one for strings.

Examples:
```
#$ffff             \ compiles 0xffff
#"string literal"  \ compiles a counted string
```

### COMPILE
Compilation tokens are compiled during compilation phase (...well, yes, it's true ;-) ).

#### COMPILE NUMBER
Compiles code that pushes a number on stack.

Example:
```
:word 1 2 3 \ define word that pushes numbers 1, 2, 3 on stack
```

#### COMPILE_STRING


#### COMPILE DEFINITION CALL
Compiles a call to a previously defined word.

Example:
```
:word1 1 2 + ; \ define word1 that adds two numbers and returns
:word2 word1 ; \ define word2 that calls word1 and returns
```

#### COMPILE DEFINITION ADDRESS
Compiles code that pushes the address of a definition on stack.

Example:
```
:word1 1 2 + ;   \ define word1
:word2 'word1 ;  \ define word2 that pushes address of word1 on stack
```

### IMMEDIATES
Immediates are not compiled during compilation phase, but executed immediately.

The syntax is like the compilation tokens, but immediate mode must be started with `[`. Immediate mode can be ended by `]`.

#### IMMEDIATE NUMBER
```
:word1 1 [ 2 ] ; \ compile word that pushes 1 when executed.
```
During compilation of `word1`, the compiler executes `2` resulting with a 2 on top of the data stack after the compilation. When `word1` is executed, 1 is pushed onto the data stack.

#### IMMEDIATE STRING

#### IMMEDIATE WORD CALL
```
:word1 1 [ word2 ] 2 ; \ executes word2 after compiling 1, but before compiling 2.
```
#### IMMEDIATE WORD ADDRESS
```
:word1 [ 'word2 ] 1 ; \ push address of word2 on stack before compiling 1.
```

### MNEMONICS
Mnemonics are the names of the CPU instructions.

### BUILDINS
Buildins are tokens that are understood by the tokenizer, and will be translated somehow to CPU instructions.

|Buildin|Description|
|-------|-----------|
|`;`    |Return|

Semicolon (`;`) returns from a word. For simple straight-line definitions,
the compiler sets the return bit on the last instruction (including generated
PUSH instructions) instead of adding `NOP.RET`. Definitions containing Immediate
code, raw data, address literals or control-flow instructions retain `NOP.RET`;
a final compiled word call in a simple definition becomes a tail jump (`JP`)
instead of `CALL NOP.RET`. Raw `call` mnemonics remain unoptimized. Tail calls
reuse the caller’s return address; code must not depend on an extra return
address for the eliminated call.

### COMMENTS
```
:word1 1 2 and ; \ This is a comment
:word2 1 ( this is a comment ) 2 and ;
```


### WHITE SPACE
There is also a token for white space. This is ignored by the compiler. It is included to be able to reconstruct the source code from the token representation.

## Variables
The initialization value of a variable is defined by a number literal.
A definition is used to label the address of the variable in memory.
```
:myvar #1 \ #1 is a number literal
:inc 'myvar @ 1 + 'myvar ! \ read variable from memory, increment, and store back to memory
```

## Build-in Words
The following words are predefined:

```forth
1+ 1-
2dup 2drop
```

Looping words:
```
if else then
while repeat
do loop
```

All looping words have to be executed immediately.

### while repeat
`while repeat` loops until the flag is 0. `while` will consume the flag.

```
:test flag [ while ] flag [ repeat ] ;
```

### do loop
`do loop` loops n times. The counter is kept on the return stack.

This will execute 3 NOPs:
```
:test 3 [ do ] nop [ loop ] ;
```


### for next
not yet implemented

`for next` works similar to a for loop in C. `for` consumes stop and start values. The loop counter can be retrieved with `i`.

This will print ABC on UART (`tx` pops a value and send it via UART):
```
:test 3 0 [ for ] 65 i + tx [ next ] ;
```

## TokenForth Examples

```forth
:min ( n1 n2 -- n )
    2dup < [ if ] drop [ else ] nip [ then ] ;
```

Hello World, for the time being implemented with "while repeat".
```forth
:msg "Hello, World!" ;
:count dup 1+ swap c@ ;
:tx $ffff c! ;
:type dup [ while ] 1- >r dup c@ tx 1+ r> dup [ repeat ] 2drop ;
[ msg count type ]
```

## TokenForth Live (prototype)

Start the local word playground with no extra dependencies:

```sh
prim live
```

Open http://127.0.0.1:8765 in a browser. Definitions compile; free code executes
in source order. For example, `:doppelt dup + ; 7 doppelt` produces `[14]`.
A definition alone does not run. `[ ... ]` executes on the separate compiler
stack, allowing the base library's `if`, `for`, and other code emitters to
modify definitions. The runtime stack starts empty; supply initial values directly in free code.

The compact runtime stack, expandable compiler stack, searchable dictionary,
and disassembly of newly generated memory update after a 350 ms typing pause.
Disassembly shows word labels and symbolic addresses. Click a dictionary name
to inspect its memory range, including base words; “Neu erzeugter Code”
returns to the newly generated code. Known literals are displayed as DATA.
Disable Live for manual execution. “Ausführung zurücksetzen” pauses before the first runtime
instruction; “Nächstes Quelltextwort” runs until the source location changes, stepping
inside user definitions and grouping internal base-word instructions.
“Nächste Instruktion” advances one CPU instruction and suspends automatic
execution. “Alles ausführen” runs to completion and restores Live behavior. Editing
source resets the step position; “Ausführung zurücksetzen” also clears both runtime stacks.
The active instruction is highlighted, including calls into base words. The
return stack is shown below the data stack; changed values are highlighted.
Stepping replays from fresh state up to the requested instruction budget;
compiler Immediate execution runs normally. “Übersetzung zurücksetzen” stops before
the first relevant token. “Nächstes Token” processes one token, skipping whitespace
and comments, and selects the next source token. Compiler stack changes and
new or modified code bytes are highlighted. Immediate words execute fully
within a token step. Token stepping uses a complete initial tokenization, so
lexically invalid or unresolved source must be corrected before stepping. Free code uses a temporary CPU
execution area, whose current instruction is displayed while paused there. Dictionary order starts descending and can be reversed. Stack
tops are on the right; results are unsigned 16-bit values. Inputs accept
decimal or `$`/`0x` hexadecimal. The disassembly is a raw code view; embedded
data can appear as instructions.

Each preview starts from fresh memory with separate compilation/runtime step
budgets and stack bounds checks. Runtime errors retain the generated code and
initialized dictionary entries. Incomplete source reports an error. The read-only memory view shows 256 bytes with hex and ASCII, navigation
by hexadecimal address, and shortcuts to HERE or the selected dictionary word.
Green bytes changed since the previous snapshot; underlined bytes differ from
the initial library memory. Inspection does not read UART or other MMIO.
Compiler and runtime errors mark their source token and line number in red.
Errors inside base words point to the call in the editor. Editing clears the
previous error marker.
Source, Live/base settings, dictionary order and memory address are remembered
in browser local storage. “Beispiel laden” restores the initial loop example
and enables base words. There is no memory editor or UART display.

The “Basiswörter” checkbox enables the base words by default. Disable it to
start with only H and LATEST (CPU mnemonics remain available). With a custom
`--library`, the checkbox controls that library instead.
The default library is prepared at startup: startup compiles bootstrap, opcode
emitters and base directly from the repository sources, without a prior build.
Use `--library other.tf.toml` to replace this library, or `--port 8766`
to select another local port. Outside the source checkout, supply `--library`.
Stop the server with Ctrl+C.
